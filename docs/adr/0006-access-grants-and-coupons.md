# ADR 0006 — Access is grants; coupons and payments both create them

**Status:** accepted (2026-10-05)

## Context

KodxCamp has to answer one question, constantly: **can this user open this resource?**

Resources are courses, roadmaps, and (later) cohorts. Users get access by:
- Redeeming a coupon code
- Paying
- Being granted access by an admin (founder comps)

We could model each source of access differently, or unify them.

## Decision

**One table: `access.grants`. Every source of access creates a grant.**

```
grants
  user_id
  scope_type      ('course' | 'roadmap' | 'cohort' | 'all')
  scope_code      (nullable when scope_type = 'all')
  source          ('coupon' | 'purchase' | 'admin')
  source_ref      (coupon id, payment id, or NULL for admin)
  granted_by      (admin user id, nullable)
  granted_at
  expires_at      (nullable = lifetime)
  revoked_at
  revoked_reason
```

Every gate check queries for a matching grant:
- Non-revoked
- Non-expired
- Scope matches the resource directly, OR matches a roadmap that contains the resource, OR `all`.

Coupons are a **separate** table (`access.coupons`). Redeeming a coupon:
1. Validates the coupon (active, not expired, not over its redemption limit).
2. Checks the user hasn't already redeemed it.
3. Creates a grant with `source='coupon'` and `source_ref=<coupon id>`.
4. Increments `coupons.redeemed_count`.
5. All in one transaction.

Payments (later) will similarly create a grant with `source='purchase'`.

Admin grants create a grant with `source='admin'` and `granted_by=<admin id>`.

## Why one table

- **Single source of truth.** "Can this user open this?" is one query.
- **Easy auditing.** `SELECT * FROM grants WHERE user_id = X` shows the full access history.
- **Simple revocation.** One `UPDATE` revokes, regardless of source.
- **Migration path.** When payments launch, they plug into an existing system instead of a parallel one.
- **Roadmaps work naturally.** A roadmap grant unlocks every course inside it without special-casing.

## Why not a JSON column on users

- Can't efficiently index.
- Can't query "who has access to course X?" (needed for admin).
- No expiry, no revocation granularity.
- Migrations become painful.

## Why not separate tables per source

- Three tables means three gate checks, three UI paths, three audits.
- Roadmap + payment + coupon would each need their own "does this unlock course X?" logic.
- One table means one gate check.

## Coupons: design choices

### Long random codes

Codes are uppercase alphanumeric, 10-16 characters, generated by `crypto.randomBytes`. Not words. Not short.

**Why:** short codes are guessable. A brute-force attack could redeem thousands. Long codes make guessing impractical even at high rate limits.

### Single-use per user

`UNIQUE (coupon_id, user_id)` in `coupon_redemptions`. A user can't redeem the same code twice.

### Campaign labels

Every coupon has an optional `campaign` field (`college-x`, `twitter-launch`, `beta-1`).

**Why:** to know which source brings real learners. A college drive that yields 5% active users is less valuable than a Twitter thread that yields 40%, even if the thread yielded fewer total signups.

### Bulk creation

`POST /admin/coupons/bulk` creates N codes at once with the same settings. CSV export for offline distribution.

## Gate check query

```sql
SELECT EXISTS (
  SELECT 1 FROM access.grants
  WHERE user_id = $1
    AND revoked_at IS NULL
    AND (expires_at IS NULL OR expires_at > now())
    AND (
      scope_type = 'all'
      OR (scope_type = 'course' AND scope_code = $2)
      OR (scope_type = 'roadmap' AND scope_code = ANY($3::text[]))
      OR (scope_type = 'cohort' AND scope_code = $4)
    )
) AS allowed
```

`$3` is the list of roadmap codes that contain the course. Computed once from the content index and cached in-process.

## Consequences

**Positive:**
- One gate check everywhere.
- Adding payment later is trivial.
- Roadmap grants work without special-casing.
- Revocation is one `UPDATE`.
- Full audit trail of how every user got access.

**Negative:**
- Every gate check is a DB query. (Mitigated by short-lived in-process caching.)
- Grants table grows over time. (Fine for our scale; could partition later.)
- Deleting a grant without a reason leaves a mystery. (Fix: always set `revoked_reason`.)
